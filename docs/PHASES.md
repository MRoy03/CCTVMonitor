- [ ] **Phase 3 — Screen Sharing Monitoring**
  - [x] `POST /cameras/{id}/frames` — accepts one JPEG frame per call, runs it through the same `process_frame` pipeline as upload/RTSP
  - [x] `cip/services/ingestion/live_tracker_registry.py` — keeps one tracker alive per camera across independent HTTP requests (frames arrive as discrete POSTs, not a pull loop, so the tracker can't live on a call stack the way StreamManager's does)

  - [x] Frontend: `/sources/new/screen-share` — `getDisplayMedia` capture, local preview/confirm, canvas-to-JPEG loop posting every 2s; camera detail page's live view now covers screen-capture cameras too
  - [x] **Verified end-to-end with real YOLO detection**: posted a real test frame (bus + 4 people) through the actual endpoint, got back real detections (94%/89%/88%/86%/62%) — confirmed through direct backend calls after the memory investigation below
  - [x] **Real bug found and fixed**: `process_frame()` originally called `asyncio.run()` internally, which works from sync contexts (Celery tasks, the StreamManager) but crashes with "asyncio.run() cannot be called from a running event loop" when called from an already-async FastAPI endpoint. Fixed by making `process_frame` itself `async` — each caller now runs it appropriately (`asyncio.run(...)` from sync code, plain `await` from async code).
  - [ ] **Significant finding: this dev machine is memory-constrained (8GB total, often <1GB free under this stack)**. Running frontend + backend + Celery + StreamManager(with a loaded YOLO model) + ffmpeg + mediamtx simultaneously pushed free RAM low enough that OpenBLAS (used by PyTorch/YOLO) failed to allocate memory outright — this looked like an application bug at first (a confusing/stale-looking traceback) before the real cause (memory exhaustion, confirmed via `wmic OS get FreePhysicalMemory`) was found. **Implication**: don't run the full stack plus multiple concurrent live-camera processes (each loads its own YOLO instance) on this machine without watching memory; one camera at a time is safer for local dev. This gets easier once deployed to Fly.io, which can be given a dedicated memory allocation.
  - [ ] Known UX gap: no global "capture active" banner outside the capture page itself (per the architecture plan's nice-to-have) — if the user navigates away, the capture loop's `setInterval` is cleaned up on unmount, stopping the capture (matches `getDisplayMedia`'s own page-lifetime constraint, but not explicitly signposted elsewhere in the UI yet)
